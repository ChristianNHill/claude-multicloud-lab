01

The Messages API

First call, streaming, and token anatomy.

Before you think about cloud platforms, learn the primitive. The Anthropic Messages API is the same interface regardless of which backend you use: Bedrock, Vertex, or direct. Get comfortable with it here. In Act 2 you'll swap the client constructor.

1.1

Run your first inference call

Run the basic inference script for the direct API. Read the output carefully: the text and all three metadata fields below it. What does stop_reason mean?

SHOW command & output
terminal 
python labs/01_basic_inference/bedrock.py   # or vertex.py / foundry.py
result
[Bedrock] A foundation model is a large neural network trained on broad data
that can be adapted to many tasks. Unlike task-specific models, it provides a
general capability base that developers build applications on top of.

  stop_reason=end_turn  input_tokens=28  output_tokens=44
stop_reason anatomy end_turn = the model finished naturally. max_tokens = the response was cut off at your limit. tool_use = the model wants to call a function (Act 3). Always check stop_reason. A truncated response that looks complete is a common production bug.
1.2

Stream the same call

Run the streaming version. Watch how the output appears differently. Then look at the code: what changes between a non-streaming and streaming call in the SDK?

SHOW command & key difference
terminal 
python labs/02_streaming/bedrock.py
non-streaming vs streaming 
# non-streaming, waits for full response
response = client.messages.create(...)
print(response.content[0].text)

# streaming: tokens arrive as generated
with client.messages.stream(...) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
final = stream.get_final_message()   # usage only available after stream closes
What this teaches The SDK exposes streaming as a context manager with an iterator. You print tokens as they arrive. Without streaming, users wait for the full generation before seeing anything. For responses over ~100 tokens, the perceived latency difference is significant. Every production chat interface uses streaming. Note that usage (token counts) is only available after the stream closes via get_final_message().
1.3

Feel what token limits do

Open labs/02_streaming/bedrock.py and change max_tokens=512 to max_tokens=10. Run it again. What changes in the output and in the metadata?

SHOW the result
truncated result

max_tokens is a hard ceiling. The model doesn't summarize. It stops. This is a common source of truncated production responses. Always set max_tokens high enough for your expected output, and always check stop_reason in the response.

03

Tool use & stateful agents

Beyond a single response.

A single messages.create() call returns text. An agent is a loop: the model can emit a tool_use block, you execute the function, and you send the result back. The model keeps going until it decides it's done. This loop is the foundation of every production AI agent.

3.1

Run the tool use lab

Run the tool use script. Watch the terminal: you should see the model call a tool or two, then synthesize the results. Look at the code: where does the loop live? What ends it?

SHOW the command & what to look for
terminal 
python labs/03_tool_use/bedrock.py
result
[Bedrock tool use]

  → calling get_weather({'city': 'San Francisco'})
  → calling get_weather({'city': 'Seattle'})

San Francisco is warmer at 17°C (partly cloudy) vs Seattle at 14°C
(overcast). San Francisco wins by 3 degrees.
the agentic loop, simplified 
while True:
    response = client.messages.create(tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": response.content})

    if response.stop_reason == "end_turn":
        break           # model is done. Print text

    if response.stop_reason == "tool_use":
        results = []
        for block in response.content:
            if block.type == "tool_use":
                output = run_tool(block.name, block.input)
                results.append({"type": "tool_result", ...})
        messages.append({"role": "user", "content": results})
One subtlety, and Lab 03 doesn't handle it. The loop above branches on stop_reason == "tool_use", which reads most clearly and matches labs/03_tool_use/bedrock.py. It breaks when a response hits the token ceiling mid-turn: stop_reason comes back max_tokens while response.content still holds complete tool_use blocks, and those calls get dropped with no error. The production form checks response.content for tool_use blocks first and uses stop_reason only as the exit condition. You'll see it in Lab 06. Compare the two loops side by side.

What this teaches State lives in a plain Python dict, outside the model, in your code. The model reads and writes it only through tools: make_plan sets the agenda, record_finding accumulates results, get_state lets it check progress. The model orchestrates; your code holds state. This separation is what makes agents resumable, inspectable, and safe to interrupt. Production agents extend this pattern with databases, queues, and human-approval checkpoints. The core loop is the same.

MCP

Tools as a separate process. ~10 min.

In Act 3, tools were defined in the same file as the agent. With MCP (Model Context Protocol), the tool definitions and implementations live in a separate process. The client discovers them at runtime over a standard protocol. You can update tools without touching model code, and any MCP-compatible client can use the same server.

What this teaches The client called session.list_tools() at startup. The server responded with its tool manifest, and the client converted that into the Anthropic tool format on the fly. No tools are hardcoded in the client. Add a tool to the server, restart it, and the client discovers it automatically without a code change. Tools and models are independently deployable.

SHOW the implementation
add to server.py 
@app.tool(
    name="get_doc_by_id",
    description="Retrieve a specific document by its ID.",
)
def get_doc_by_id(id: str) -> str:
    log.info("get_doc_by_id(%r)", id)
    match = next((d for d in DOCS if d["id"] == id), None)
    if not match:
        return f"No document found with id: {id!r}"
    return f"[{match['id']}] {match['title']}\n{match['body']}"

Debrief

When do Bedrock and Vertex matter?

When data residency, VPC egress, or existing cloud billing agreements drive the decision. The code difference is one constructor. The operational difference, IAM, audit logs, network topology, is significant. Most enterprises that care about one of these things care about all three.

Why use AnthropicBedrock/AnthropicVertex instead of the raw cloud SDK?

The Anthropic SDK handles auth, retries, streaming normalization, and type safety across backends. Using boto3.client("bedrock-runtime") directly means managing all of that yourself, plus keeping up with Anthropic's API changes by hand. The first-party backends exist exactly to avoid that.

Why does Foundry use a different format for tool calls?

Azure AI Foundry uses an OpenAI-compatible API surface across all its models. That's a deliberate platform choice: existing OpenAI tooling works with any Foundry model, at the cost of diverging from the native Anthropic format. A thin adapter at the tool-dispatch layer handles this.

When is MCP worth the extra process?

When tools need to be shared across multiple models or clients, when they're deployed and updated independently, or when the tool itself is a service rather than a function. For a single-model script, hardcoded tools are simpler. For a platform where many agents share a tool catalog, MCP earns its overhead.

What's missing from this lab?

Prompt caching, which cuts costs dramatically on repeated large-context calls. Token counting (pre-flight cost estimation before sending a request). Managed agents with server-side tool execution. These are the next layer. Once you understand the primitives, those APIs will make sense.

Back to the thesis. One constructor swap moves the same code between Bedrock, Vertex, and Foundry. The agentic loop, model calls tool, you run it, feed it back, is the same on all three. MCP decouples tools from the agent so both can evolve independently. The stateful agent shows what that loop looks like when you add memory, planning, and multi-step orchestration. These are the building blocks. Everything production runs on them.
